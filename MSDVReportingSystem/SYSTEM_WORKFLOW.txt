1. SYSTEM OVERVIEW
==============================================================================

The MSDV Reporting System is a comprehensive web-based platform designed for
institutional management of student discipline, violations reporting, and
appeals processing. It enables multiple stakeholders (students, teachers,
administrative staff) to participate in a structured workflow for reporting
and managing student misconduct.

Core Purpose:
- Allow authorized staff to report student violations
- Centralize violation records management
- Track disciplinary actions and sanctions
- Process student appeals for violations
- Maintain comprehensive student records
- Generate reports and analytics on violations

Deployment Environment:
- Server: Apache (XAMPP)
- Database: MySQL
- Language: PHP
- Frontend: HTML, CSS, JavaScript, Bootstrap
- Database: PDO (PHP Data Objects)

4. COMPLETE SYSTEM WORKFLOW
==============================================================================

4.1 USER AUTHENTICATION FLOW
─────────────────────────────

1. User Access System
   └─> Open index.html (Login Page)

2. User Inputs Credentials
   └─> Enter Username and Password
   └─> Optional: Check "Remember Me"

3. Credentials Submitted to login.php
   └─> POST request to /login.php

4. Server Authentication Logic
   └─> Query database for username
   └─> Verify hashed password
   └─> IF invalid → Redirect to index.html with error
   └─> IF valid → Continue to step 5

5. Session Creation
   └─> SET $_SESSION['user_id'] = user ID
   └─> SET $_SESSION['username'] = username
   └─> SET $_SESSION['full_name'] = full name
   └─> SET $_SESSION['role'] = user role
   └─> SET $_SESSION['is_first_login'] = first login flag

6. Remember Me Feature (if checked)
   └─> Generate remember_token (random hash)
   └─> Store token in users table with expiration
   └─> Set remember_token cookie (persistent)

7. Role-Based Redirect
   └─> IF role = 'admin' → /admin/dashboard.php
   └─> IF role = 'student' → /student/dashboard.php
   └─> IF role = 'teacher' → /teacher/report-form.php
   └─> IF role = 'csu' → /csu/report-form.php
   └─> IF role = 'jassu' → /jassu/report-form.php

4.2 FIRST LOGIN PASSWORD CHANGE FLOW
─────────────────────────────────────

1. User Logs In First Time
   └─> is_first_login = 1 in database

2. Upon Landing in Assigned Area
   └─> System detects first login flag
   └─> Prompts user to change password immediately

3. User Submits New Password
   └─> Validates: Password matches confirmation
   └─> Validates: Minimum 6 characters
   └─> Hash new password using PASSWORD_DEFAULT

4. Password Updated
   └─> UPDATE users SET password=hashed
   └─> UPDATE users SET is_first_login=0
   └─> Clear remember_token cookie

5. Session Destroyed & Redirect
   └─> User session ends
   └─> Redirect to login.php
   └─> User logs in again with new password

4.3 VIOLATION REPORTING WORKFLOW (Teacher/CSU/JASSU)
────────────────────────────────────────────────────

1. Staff Member Accesses Report Form
   └─> Navigate to /teacher/report-form.php
   └─> OR /csu/report-form.php
   └─> OR /jassu/report-form.php

2. Form Submitted with Violation Details
   Select student ID:
   └─> Verify student exists in database
   └─> IF not found → Display error, request valid ID

3. Report Details Entered
   └─> Category: (Minor/Major)
   └─> Violation Type: (specific violation)
   └─> Description: (detailed explanation)
   └─> Evidence: (optional photo upload)

4. Upload Evidence (Optional)
   └─> IF evidence file selected
   └─> Validate file (check type, size)
   └─> Move file to /uploads/directory
   └─> Store filename in database

5. Violation Record Created
   INSERT INTO violations
   └─> student_id
   └─> violation (violation type)
   └─> description
   └─> category (minor/major)
   └─> evidence_path (if uploaded)
   └─> submitted_by (staff member ID)
   └─> date_submitted (current date/time)
   └─> status = 'pending'

6. Notification Generated
   └─> Send notification to Admin
   └─> Message: "New violation report from [Staff Name]"
   └─> Link: /admin/violation-records.php

7. Confirmation Displayed
   └─> Show success message
   └─> Provide violation reference number

4.4 STUDENT VIOLATION VIEWING FLOW
──────────────────────────────────

1. Student Logs Into Dashboard
   └─> Navigate to /student/dashboard.php

2. System Fetches Student's Violations
   └─> Query violations table WHERE student_id = current_student
   └─> Join with disciplinary_actions table
   └─> Join with appeals table

3. Violations Displayed to Student
   For each violation, show:
   └─> Violation type
   └─> Category (minor/major)
   └─> Date reported
   └─> Description
   └─> Evidence (if available)
   └─> Disciplinary action status (if assigned)
   └─> Sanction details (if applicable)
   └─> Appeal status (if appeal exists)

4.5 DISCIPLINARY ACTION WORKFLOW (Admin)
────────────────────────────────────────

1. Admin Accesses Violation Records
   └─> Navigate to /admin/violation-records.php
   └─> View pending violations requiring action

2. Admin Initiates Disciplinary Action
   └─> Select a violation
   └─> Review violation details and evidence
   └─> Determine appropriate sanction

3. Create Disciplinary Action
   INSERT INTO disciplinary_actions
   └─> violation_id
   └─> student_id
   └─> sanction (type/duration)
   └─> status = 'pending'
   └─> start_date = null (set when approved)
   └─> end_date = null (set when completed)

4. Admin Updates Status
   Location: /admin/disciplinary-action.php
   Status Flow (One-way only):
   └─> pending → ongoing → completed

   When status changed to 'ongoing':
   └─> Set start_date = current date
   └─> Update violations table status

   When status changed to 'completed':
   └─> Set end_date = current date
   └─> Officially close the case

5. Student Notified
   └─> INSERT INTO notifications
   └─> Message: "Your disciplinary case status updated to: [STATUS]"
   └─> Link: /student/dashboard.php

4.6 STUDENT APPEAL WORKFLOW
──────────────────────────

1. Student Reviews Violation
   └─> Access /student/dashboard.php
   └─> View violation they wish to appeal

2. Student Submits Appeal
   └─> Click "Appeal" button on violation
   └─> Write detailed appeal explanation
   └─> Submit appeal form

3. System Validates
   └─> Check if appeal already exists for this violation
   └─> IF yes → Display error "Appeal already submitted"
   └─> IF no → Continue

4. Appeal Record Created
   INSERT INTO appeals
   └─> violation_id
   └─> student_id
   └─> explanation (student's reason for appeal)
   └─> submitted_at = current timestamp
   └─> status = 'pending'

5. Admin Notified
   └─> INSERT INTO notifications to admin
   └─> Message: "Student [ID] submitted an appeal"
   └─> Link: /admin/student-appeals.php

6. Success Message
   └─> Display confirmation
   └─> Inform student appeal is under review

4.7 ADMIN APPEAL REVIEW WORKFLOW
─────────────────────────────────

1. Admin Accesses Appeals Panel
   └─> Navigate to /admin/student-appeals.php

2. Admin Reviews Appeal
   └─> View student name
   └─> Review violation details
   └─> Read student's appeal explanation
   └─> Examine evidence

3. Admin Makes Decision
   
   Option A: Approve Appeal
   └─> Determine violation was unjustified
   └─> Click "Approve" button
   └─> System automatically:
       ├─> UPDATE appeals SET status='approved'
       ├─> DELETE FROM appeals (all for that violation)
       ├─> DELETE FROM disciplinary_actions (for that violation)
       ├─> DELETE FROM violations (completely remove)
   └─> Send notification to student: "Appeal APPROVED. Violation removed."

   Option B: Reject Appeal
   └─> Determine violation was justified
   └─> Click "Reject" button
   └─> System:
       ├─> UPDATE appeals SET status='rejected'
   └─> Send notification to student: "Appeal REJECTED. Violation remains on record."

4. Student Notification
   └─> INSERT INTO notifications (student user)
   └─> Message with appeal decision
   └─> Link: /student/dashboard.php

4.8 ADMIN DASHBOARD ANALYTICS FLOW
──────────────────────────────────

1. Admin Logs In
   └─> Redirected to /admin/dashboard.php

2. Dashboard Loads Data
   Key Statistics Calculated:
   └─> Total Students Count
   └─> Total Violations Count
   └─> Pending Disciplinary Cases
   └─> Completed Cases
   └─> Unread Notifications

3. Charts Generated (via AJAX)
   └─> Monthly violations trend
   └─> Minor vs Major violations ratio
   └─> Violations by category
   └─> Violations by department
   └─> Status distribution (pending/ongoing/completed)

4. Notifications Displayed
   └─> Fetch latest 20 notifications
   └─> Display in notification panel
   └─> Mark as read when clicked

4.9 USER MANAGEMENT WORKFLOW (Admin Only)
──────────────────────────────────────────

1. Admin Accesses User Management
   └─> Navigate to /admin/user-management.php

2. Add New User
   └─> Click "Add New User"
   └─> Enter: Full Name, Username, Email, Password, Role
   └─> Validate:
       ├─> Username must be unique
       ├─> Passwords must match
   └─> INSERT INTO users
   └─> Set is_first_login = 1 (force password change)

3. Edit Existing User
   └─> Select user
   └─> Modify: Full Name, Username, Email, Role
   └─> UPDATE users table

4. Change User Password
   └─> Select user
   └─> Admin enters new password
   └─> Validate passwords match
   └─> Hash and UPDATE users.password

5. Delete User
   └─> Select user (must not be admin or student)
   └─> Admin enters deletion password: "delete123"
   └─> IF password correct → DELETE FROM users
   └─> IF password incorrect → Show error

4.10 STUDENT RECORDS MANAGEMENT

1. Admin Accesses Student Records

2. Search Students

4.11 PASSWORD MANAGEMENT
────────────────────────

First Login Password Change:
1. New user logs in
2. System detects is_first_login = 1
3. Mandatory password change modal
4. User enters new password (min 6 chars)
5. Password hashed and saved
6. is_first_login set to 0

Admin Password Change:
1. Admin navigates to /admin/change-admin-password.php
2. Enters current password
3. Enters new password (min 6 chars)
4. Confirms new password
5. System validates current password
6. Updates users.password

Logout:
1. User clicks Log Out
2. Session destroyed
3. remember_token cookie cleared
4. Redirect to login page

5.3 AUTHENTICATION & SECURITY
──────────────────────────────

Session Management:
- Session started automatically
- Session ID stored in $_SESSION array
- session_start() called at top of each page
- Cache headers prevent backdating

Password Security:
- Passwords hashed using PASSWORD_DEFAULT (bcrypt)
- Password verification with password_verify()
- Minimum password length: 6 characters

Token-Based Remember Me:
- 30-day persistent login tokens
- Random token generated on login
- Token stored in database with expiration
- Token validated on each visit

Authorization:
- auth_guard.php provides requireLogin() function
- Role-specific access control validated
- Unauthorized access redirects to login

Cache Prevention:
- HTTP headers disable browser cache
- Pragma: no-cache
- Cache-Control: no-store
- Expires: past date
- Prevents back button on protected pages

5.4 FILE UPLOAD HANDLING
────────────────────────

Evidence Upload:
- Location: /uploads/ directory
- Allowed types: Image files
- File validation on server-side
- Files stored with timestamp + original name
- Path stored in violations.evidence_path

Upload Processing:
1. File submitted in form
2. Validate file exists and has content
3. Generate unique file name
4. Move to uploads directory
5. Store path in database
6. Return to form with confirmation

7.4 DATA INTEGRITY & CASCADING DELETES
───────────────────────────────────────

Automatically removes:
- All appeals for that violation
- Associated disciplinary actions
- The violation itself

This maintains referential integrity:
- No orphaned records
- Complete removal of dismissed violations
- Clean data state

7.5 EVIDENCE MANAGEMENT
───────────────────────

File Storage:
- Location: /uploads/ directory
- Naming: timestamp_originalname
- Types: Images (jpg, png, gif)
- Access: Only through authorized links

Retrieval:
- Path stored in violations table
- Accessible through violation record
- Admin can view evidence
- Student can view evidence against them

7.6 PASSWORD SECURITY
─────────────────────

Password Requirements:
- Minimum 6 characters
- Hashed with bcrypt (PASSWORD_DEFAULT)
- Never stored in plain text
- Verified using password_verify()

Password Reset:
- First-time users must change password
- Forced modal on login
- Cannot proceed without changing
- remember_tokens cleared

Admin Functions:
- Can reset any user password
- Can change own password
- Requires current password verification

7.7 REMEMBER ME FUNCTIONALITY
─────────────────────────────

Token-Based Persistent Login:
1. User checks "Remember Me"
2. System generates random token
3. Token stored in users table
4. Token also stored in cookie (30 days)
5. On next visit, token auto-authenticates
6. User session created automatically
7. No login required

Token Expiration:
- Automatic database cleanup
- Token invalidated if expired
- require_token check on each visit

7.8 VIOLATION LIFECYCLE
───────────────────────

Pending Status:
- Just reported
- Awaiting admin review
- No sanction assigned yet

Ongoing Status:
- Admin approved sanction
- Disciplinary action started
- Start date recorded
- Student serving consequences

Completed Status:
- Disciplinary action finished
- End date recorded
- Case closed (unless appealed)
- Record maintained for history

Appeal Status:
- Can only appeal pending violations
- Once approved, violation removed
- Once rejected, must accept violation
- No status change possible

7.9 STATISTICS & REPORTING
───────────────────────────

Admin Dashboard Shows:
- Total students count
- Total violations count
- Pending sanctions count
- Completed cases count
- Unread notifications count

Charts Available:
- Monthly violations trend
- Violation category breakdown
- Violations by department
- Status distribution
- Severity analysis

Reports Accessible Via:
- All users: /[role]/my-reports.php
- Admin: Comprehensive analytics
- Staff: Submitted reports only

8. SECURITY & SESSION MANAGEMENT
==============================================================================

8.1 SESSION LIFECYCLE
─────────────────────

Session Start:
- Initiated at login.php
- $_SESSION populated with user data
- remembered via cookie (if enabled)

Session Duration:
- Default PHP session timeout
- Continue while browser open
- Persistent across pages
- Ended at logout

Session Cleanup:
- On logout: session_destroy()
- On appeal: remember tokens cleared
- On password change: tokens cleared
- On credential fail: no session created

8.2 AUTHENTICATION FLOW SECURITY
─────────────────────────────────

Login Process:
1. Username validated in database
2. Password hashed and compared
3. No direct password comparison
4. Failed attempts not logged (privacy)
5. Generic error messages (prevent username enumeration)

Remember Me Security:
1. Random token generated (unguessable)
2. Token expires after 30 days
3. Token specific to user
4. Token invalidated on:
   - Password change
   - Password reset
   - Logout
   - Appeal submission

5. Token verified before session creation

8.3 AUTHORIZATION CHECKS
────────────────────────

Every Protected Page:
- Checks session exists
- Validates user_id set
- Confirms role matches requirement
- Denies access if not authorized

Admin-Specific Pages:
- Require role='admin'
- Student role explicitly denied
- Redirect to login on failure

Staff Roles (teacher/csu/jassu):
- Share report-form.php
- Array check for allowed roles
- Each role has own directory

Student-Specific:
- Require role='student'
- Can only see own violations
- Cannot access admin areas

8.4 CACHE PREVENTION HEADERS
──────────────────────────────

Every Protected Page Sends:
- Cache-Control: no-store, no-cache, must-revalidate, max-age=0
- Pragma: no-cache
- Expires: Sat, 01 Jan 2000 00:00:00 GMT

Purpose:
- Prevent browser caching
- Disable back button
- Force fresh page load
- Protect sensitive data

Applied When:
- User loads any protected page
- AJAX requests
- Redirect responses

8.5 DATA VALIDATION
───────────────────

Input Validation:
- trim() removes whitespace
- isset() checks variables exist
- Type casting for integers
- Database prepared statements (prevent SQL injection)

Prepared Statements:
- All database queries use ?
- Parameterized queries
- User input separated from SQL
- Protection against injection attacks

8.6 SENSITIVE DATA PROTECTION
──────────────────────────────

Passwords:
- Hashed with PASSWORD_DEFAULT
- Never logged or displayed
- Verified with password_verify()
- Minimum 6 characters enforced

Tokens:
- Random generated (unguessable)
- Stored hashed in database
- Cookies set with session_set_cookie_params
- Cleared on sensitive actions

Student Data:
- Student records private
- Accessible only to student themselves
- Admin can access for management
- Staff can only submit violations

Evidence Files:
- Stored outside web root
- Access controlled
- Authentication required to view
- Cannot be directly accessed
